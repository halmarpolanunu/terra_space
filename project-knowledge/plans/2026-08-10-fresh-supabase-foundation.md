# Fresh Phase-Prefixed Supabase Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a fresh, phase-prefixed PostgreSQL schema in the existing local Supabase deployment without deleting or rewriting the current SQLite database or legacy Supabase tables.

**Architecture:** One checked-in Supabase SQL migration owns tables, constraints, indexes, comments, reference-data transfer, and authority-preserving database functions. The new schema is created beside legacy tables, tested while all n8n workflows remain inactive, and becomes writable only through later plans.

**Tech Stack:** Local Supabase/PostgreSQL, SQL migrations, PostgreSQL JSONB, SQLAlchemy-compatible UUIDs, PowerShell backup helpers, Supabase advisors.

## Global Constraints

- Never drop, truncate, rename, or delete an existing table or row in this plan.
- Preserve the current SQLite database unchanged and create a dated backup before applying DDL.
- Use the `public` schema and literal `phase1_`, `phase2_`, and `phase3_` table prefixes.
- Add a plain-language PostgreSQL `COMMENT` to every new table and every non-obvious status, identity, evidence, authority, and audit column.
- Keep browser clients away from database credentials; backend and n8n will use private local credentials in later plans.
- Keep all four n8n workflows inactive.
- Apply DDL through a checked-in migration and the Supabase migration mechanism, never ad-hoc destructive SQL.
- Stop and ask the owner before any destructive correction if the migration partially applies.

# Execution notes

Recorded on 2026-08-10, when this plan was carried out. Everything below is a difference between
what the plan said and what the machine actually offered, not a change of intent.

- **The SQLite backup helper is at the repository root**, `Backup-TerraSpaceDatabase.ps1`, not in
  `tools/`. The existing helper was used unchanged.
- **There is no Supabase CLI on this computer.** The local Supabase deployment is a Docker stack
  whose project folder, `D:\local-supabase`, contains only `config.toml` and saved query snippets -
  no migrations folder. Every earlier migration was applied straight to the database and recorded
  in its `supabase_migrations.schema_migrations` table. This plan followed the same route: the
  checked-in file was applied once, as a whole, inside a single transaction (so a failure part-way
  would have left nothing behind), and then registered in that same table. `supabase migration list`
  now shows `202608100001 fresh_phase_prefixed_foundation`. No second hand-typed copy of the DDL
  was ever run.
- **The plan says "all 16 tables"; the approved architecture actually lists 18.** All 18 were
  created and all 18 carry a description. 72 of their 164 columns carry a column description -
  every status, identity, evidence, snapshot, authority, coordinate, and raw-output column. Plainly
  obvious columns such as `title` and `created_at` were left without one on purpose.
- **The checks that Task 4 describes live in `supabase/tests/phase3_reference_data.sql`**, not
  inside the seed file, so they can be re-run on their own at any time without loading anything.
- **Two advisor warnings were caused by this migration and both were fixed inside it**: the two new
  functions were given a fixed `search_path`, and the browser-facing `anon` and `authenticated`
  roles had their automatic `SELECT` grant taken away from all 18 tables. Row Level Security alone
  already hid the rows, but the grant still exposed table and column names through Supabase's
  generated GraphQL schema. The browser-facing key is now refused outright.
- **The advisor errors that remain are all pre-existing and were left alone.** Twelve
  `rls_disabled_in_public` errors are on legacy tables, including the `terra_space_*` tables the
  four workflows read and write today. Turning Row Level Security on there would change how the
  working pipeline behaves, which is outside this plan and would need the owner's decision.
- **The `phase3_events.epistemic_status`, `origin`, and `dashboard_status` columns are required**
  and pipeline events must carry a candidate key, a Phase 1 source, and an outcome. The plan listed
  the allowed values but not whether the columns could be blank; requiring them keeps an event from
  existing without the identity it needs to be traced.
- **Non-leaf taxonomy nodes have no description.** Only Event Types have approved descriptions, and
  inventing text for Domains, Categories, and Subcategories would have created placeholder
  information.

# Completion gate

Do not begin the n8n transition until all new tables exist, comments are readable, authority-function tests pass, reference counts reconcile, legacy data is untouched, all workflows remain inactive, and the owner receives the verification summary.
